# Content Pipeline — html, jsx, md

The publishing pipeline is: client posts raw code → `detectType` decides what it is → `wrap{Type}` produces the served HTML → S3 stores the wrapped HTML with a marker comment → `/raw` un-wraps using the marker for round-tripping in the editor. All the logic lives in `services/content.js`; the un-wrap path lives in `routes/api.js` (`GET /api/pages/:slug/raw`). Keep these in sync.

## Detection — `detectType(code)`

Returns `"html"`, `"jsx"`, or `"md"`. The logic is deliberately heuristic and cheap.

**Strong signals first** — anything starting with `<!doctype html>` or `<html>` is html, end of story.

**Markdown signals** (count how many match, need ≥3 to call it md):

- `^#{1,6}\s+\S` (heading)
- `^(?:[-*+])\s+\S` (bullet)
- `^>\s+\S` (blockquote)
- ```` ^``` ```` (code fence)
- `[text](url)` (link)
- `![alt](url)` (image)
- `^\d+\.\s+\S` (numbered list)
- `^---\s*$` (horizontal rule)
- `\*\*text\*\*` (bold)

**JSX/React signals** (count how many match, need ≥2 to call it jsx — but a hint plus html-shape falls back to html, and a single jsx hint alone with no html shape goes to jsx):

- `import ... from 'react'`
- `export default (function|class)`
- `function|const|class App|Main|Page|Home|Dashboard`
- `useState(` / `React.useState`
- `useEffect(` / `React.useEffect`
- `ReactDOM`
- `<Tag className=...`
- `return (<`

**Tie-breaking** — jsx wins over md wins over html, in the sense that we check jsx signals before falling through to md count again. Read the code in `services/content.js` for the exact precedence.

**Why heuristic?** This is on the publish hot path. Parsing the AST or running a real markdown lexer would add latency and dependencies. The cost of a wrong detection is one re-publish with explicit type, which the editor could expose if it ever becomes a problem.

## HTML wrapping — pass-through

For html, the code is stored as-is in `pages/{slug}.html`. Title and description are extracted for `meta.json`:

- Title: `<title>...</title>`, fallback to the slug.
- Description: `<meta name="description" content="...">`, fallback to the first `<p>` with ≥10 chars of content.
- Description is truncated to 150 chars (`... + "..."`) for the dashboard card.

No marker comment is added (html is the default — the absence of `<!-- page-type:* -->` *is* the marker).

## JSX wrapping — `wrapJsx(jsxCode, title)`

Output is a full HTML document with:

- `<!-- page-type:jsx -->` marker right after `<!DOCTYPE html>`
- React 18 + ReactDOM + Babel-standalone + Tailwind from CDN
- ES module imports for react/react-dom stripped
- A `const { useState, useEffect, ... } = React;` line generated by scanning the code for which hooks it actually uses
- `export default` statements stripped
- A render block that tries the detected default-export name first, then falls back through `App`, `Main`, `Page`, `Home`, `Dashboard`

The render fallback is for resilience: if a user pastes a JSX snippet without `export default`, we still try to find a top-level component and render it. The trade-off: a snippet with no recognisable component just won't render anything. That's fine — they can fix and re-publish.

**The marker comment is load-bearing.** `/api/pages/:slug/raw` checks `raw.includes("<!-- page-type:jsx -->")` to decide whether to un-wrap. If you ever rename or reformat the marker, you break the editor for every existing jsx page.

## Markdown wrapping — `wrapMarkdown(mdSource, title)`

Output is a full HTML document with:

- `<!-- page-type:md -->` marker
- `<!-- md-source:{base64(mdSource)} -->` — the original markdown, base64-encoded, so the editor can round-trip
- A baked-in dark theme (Inter font, JetBrains Mono for code, orange accents)
- `<article>` wrapping the marked-rendered body

The base64 round-trip is the workaround for "we want WYSIWYG-ish previews on serve, but the editor wants to show the original markdown". Base64 because raw markdown can contain HTML comment terminators (`-->`) that would break the parsing. If you're tempted to switch to plain wrapping, test with a markdown file that has `-->` in a fenced code block first.

## Un-wrapping — `GET /api/pages/:slug/raw`

The route reads the stored HTML, looks at the marker comment, and extracts the original source:

- `<!-- page-type:jsx -->` → match `<script type="text/babel">\n?(...)\n?const root = ReactDOM`, then strip the leading hook destructure line.
- `<!-- page-type:md -->` → match `<!-- md-source:(...) -->`, base64-decode.
- No marker → return the raw HTML as-is.

The response shape is `{ slug, type, source, access, tags }` — the editor uses `type` to pick a syntax mode, `access` to render the access toggle, and `tags` to pre-fill the tag chip-input when editing.

Round-tripping isn't lossless in every case (the jsx un-wrap relies on the structure of `wrapJsx`'s output). If you change `wrapJsx`, change the un-wrap regex in `routes/api.js` at the same time. Same for `wrapMarkdown`.

## On-serve injection — badge + assistant tag

When `/p/:slug` serves a page (`routes/pages.js`), it injects three things just before `</body>`:

1. **The Shipfast badge** — a fixed-position pill in the bottom-right with the orange flash icon, page view count, and link back to `/`. Inline styles, no external CSS dependency. The view count comes from a synchronous Redis read with a try/catch fallback to 0.

2. **Tag chips** (only when the page has tags) — a fixed-position row in the bottom-left, one per tag. Each is a plain `<a href="/?tag=Name">` so the chips are crawlable and click through to the dashboard filtered by that tag. Tags come from the same `getPageMeta` read used for access (one fetch, both fields), and every tag is HTML-escaped before injection since it ends up in both an attribute and text.

3. **The assistant loader tag** (only when `ASSISTANT_ENABLED && currentUser`) — `<script src="/assistant.js" data-sf-assistant data-slug="..." defer></script>`. The loader script then sets up the floating pill and iframe panel.

The injection picks the *last* `</body>` so pages with multiple body tags (shouldn't happen but possible if a user pastes weird HTML) get the injection in the right place. If there's no `</body>` at all, the badge is appended at the end.

This means: **don't put user content after `</body>`**. The badge will sneak in front of it. That's almost always desirable but if you ever need to disable injection for a specific page (e.g., embedded iframes), the cleanest hook is a meta tag check in `routes/pages.js`.

## Adding a new content type

The recipe, with the gotchas:

1. **Add detection signals** in `detectType()`. Don't be too aggressive — false positives hurt more than false negatives, because users can always re-publish.
2. **Add a `wrap{Type}()` function** that returns a complete HTML document. Start with `<!DOCTYPE html>` followed by `<!-- page-type:{type} -->` on its own line — the un-wrap path looks for that exact marker.
3. **If the un-wrap is lossy** (you transform the source for serving), base64-encode the original source into a second marker comment, like `<!-- {type}-source:{base64} -->`. The editor expects to get the original back.
4. **Update `/api/pages/:slug/raw`** in `routes/api.js` with a new `if (raw.includes("<!-- page-type:{type} -->"))` branch.
5. **Update the title-extraction logic** in `POST /api/pages` if the new type has its own title convention (e.g., the first `# Heading` for md, or a `document.title = ...` for jsx).
6. **Decide what description to show** in the dashboard listing. If the type has no obvious description source, leave it empty — better than guessing wrong.

Test by publishing a sample, navigating to `/p/{slug}` to verify it renders, then clicking "Edit" in the dashboard to verify the round-trip.
